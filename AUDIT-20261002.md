# md_llm audit — 2026-10-02

Full source audit of the working tree at `main` (`0046fce`). Analysis only — nothing was modified.
Method: six parallel read-only area reviews (chat, llm clients, reader, controls/core, docs/tunnel/sandbox, app/packaging), followed by main-session cross-module synthesis; every P1 below was independently verified against the cited code. A prior audit exists (`AUDIT-20260930.md`); this report tracks what was fixed from it and what is still open.

## Executive summary

md_llm remains well-engineered, unusually well-documented code with a genuinely clean layering (Core DI seam, stdlib-only providers, atomic-write discipline, adversarially tested sandbox-profile builder). **No P0s were found this pass** — down from three in the 2026-09-30 audit, whose P0s are verified fixed except one incompletely: the hardened-sandbox settings-file deny was added, but its `.tmp` staging-file literal never matches the actual `mkstemp` names (P1-4). The dominant problems this time are **lifetime seams**: closing a document orphans a running agent stream, an mtime-based sandbox GC silently deletes live sessions' working directories, and the launchers treat staged uploads as disposable while the Reader editor persists real user edits into them (three separate silent-data-loss paths). The other systemic weakness is **settings persistence**: half the provider controls mount from settings keys nothing ever writes (resetting every session — a known-unfinished prior finding), and the shared settings file uses unlocked whole-file read-modify-write that loses concurrent writes and silently clobbers a malformed file. One security finding tops the list: the Reader renders documents with `unsafe_allow_html=True`, which is stored XSS the moment any host renders documents it doesn't fully trust.

## Findings

### P0 — critical

None.

### P1 — important

**P1-1 · Stored XSS: document content rendered with `unsafe_allow_html=True` — `src/md_llm/reader.py:1315` (also the block view at 814-817) — reader**
The locked view renders `st.markdown(_escape_currency_dollars(text), unsafe_allow_html=True)`; the comment (1303-1305) shows the intent is merely to let `<b>`-style inline tags render, but the flag passes the document's raw HTML to the frontend unsanitized — a file containing `<img src=x onerror=...>` or an `<iframe>` executes script in the host app's origin when opened. `_escape_currency_dollars` only rewrites `$`. For the bundled single-user local app this is self-XSS; but `md_llm` is explicitly a reusable library whose hosts render shared/uploaded documents, which makes this stored XSS in any multi-user deployment (cookie/session-state theft via Streamlit's `/_stcore` endpoints). **Fix:** drop `unsafe_allow_html` (losing `<b>` rendering is acceptable) or sanitize to a whitelist (e.g. bleach-style allowlist of inline tags) before rendering.

**P1-2 · Closing a document orphans a running stream/agent — `src/md_llm/docs.py:270-271`, `302` with `src/md_llm/chat.py:1019-1021` — docs/chat seam**
Session "Close" and "Clear conversation" correctly call `_stop_streaming_reply()` first (chat.py:1657, 1767 — chat.py:1763-1766 even documents why), but the document-close paths (`_drop_doc_keys` via `remove_document`/`reset_documents`, reached from the sidebar ✕/Close and from `open_in_reader(..., keep_open=False)`) just pop `_chat_bg_task__doc__<rel>` while the worker thread — and for OpenCode/Cline/ZCode its auto-approving subprocess — keeps running. `_finalize_all_done_tasks` only scans currently-open docs, so the finished reply is silently discarded and ⏹ Stop can never reach the task again. Trigger: start a reply (agent providers are long-lived by design), close the document; the close dialog warns only about "a non-empty LLM chat". Impact: an unkillable token-spending agent and silent loss of the reply. *(Prior audit P1-7 — partially fixed; this path was missed.)* **Fix:** iterate the doc's chat sessions calling the same stop path before `_drop_doc_keys`, and surface an in-flight stream in the close warning.

**P1-3 · mtime-based sandbox GC deletes live sessions' sandboxes — `src/md_llm/sandbox.py:108`, `149` with `src/md_llm/chat.py:126-146` — sandbox/chat seam**
`clear_stale` decides staleness purely from the directory's mtime — which only changes when direct children are added/removed, not when an agent edits existing files — and `new_session_sandbox` GCs unconditionally on every creation, with no liveness tracking. A session idle >24 h (app left open overnight, or whose agent only edited files in place) has its sandbox `rmtree`d the moment *any other* session creates one; the memoized path then points at a deleted directory and the next turn silently recreates it empty (`llm.py`'s `makedirs(exist_ok=True)`), destroying the agent's prior working files mid-conversation. **Fix:** track live sandboxes explicitly (a session-state/registry of in-use roots excluded from GC), or touch a heartbeat sentinel file each turn instead of relying on directory mtime.

**P1-4 · Sandboxed agents can still read the settings file's atomic-write staging temps — `src/md_llm/sandbox.py:313-314` vs `src/md_llm/core.py:97-99` — sandbox/core seam**
The profile denies the settings file (the fix for the prior audit's P0-2) and its comment claims "The .tmp literal covers the atomic-save staging name" — but it emits `(deny file-read* (literal "{real}.tmp"))` while `save_settings` stages via `tempfile.mkstemp(prefix=basename + ".", suffix=".tmp")`, producing `_md_llm_settings.json.<random>.tmp`, which the literal never matches. The settings *directory* is listable (only `base_dir` and the settings file are denied), saves fire during a run (every chat send persists model/endpoint memory), and the agent runs as the same user with network allowed — so a prompt-injected read landing in a save window, or a staging file left by a killed process, hands the "hardened" agent the plaintext provider API keys. Verified mismatch on both sides. **Fix:** deny `(subpath "{real}.")` (prefix form) instead of the `.tmp` literal; add a regression test asserting the emitted profile matches a real mkstemp name. *(Hole in the prior P0-2 fix.)*

**P1-5 · "Hardened sandbox" silently runs unconfined when `sandbox-exec` is missing — `src/md_llm/llm.py:1274`, `1490`, `1823` with `src/md_llm/sandbox.py:58-60` — sandbox/llm seam**
All three agent send paths gate on `if hardened and sandbox.seatbelt_available()` — when the user enables Hardened but the host is non-macOS (or sandbox-exec is absent), the agent silently runs fully unconfined with network and auto-approved tools, no error and no UI warning. This contradicts the fail-closed principle the same call site enforces four lines earlier for profile-write failures ("a sandbox the user asked for that cannot be created must fail the run, never silently run it unconfined"). *(Variant of prior P1-1; the profile-write-failure half was fixed, this half wasn't.)* **Fix:** fail the run (or at minimum return a flag + surface a warning in the chat panel) when hardening was requested but the mechanism is unavailable.

**P1-6 · Fourteen mounted control values read settings keys nothing ever writes — `src/md_llm/controls.py:632, 660, 666, 678, 699, 704, 837, 853, 865, 1014, 1027, 1237, 1289, 1307` — controls**
The widget `value=` arguments read `llm_opencode_{workdir,hardened,attach,agent}`, `llm_cline_workdir`, `llm_zcode_hardened`, `llm_oai_model`, `llm_or_model`, `llm_instruction`, and the Ollama endpoint key — none of which any code path persists (verified by exhaustive grep; the only `llm.*` subkeys ever written are the model-catalog/last-model/endpoint/oai_endpoints keys plus `chat_save_dir`). `_remember_instruction` (controls.py:318) exists but is never called. Impact: a user who pins a real project as the OpenCode/Cline working directory, disables hardening, sets `--attach`/agent, or edits the instruction loses all of it on every browser restart — the workdir silently reverts to managed-sandbox mode. The prefixed `chat_*` variants can never round-trip at all, since hosts share the unprefixed `llm.*` shape. *(Prior audit P1-12 — still open.)* **Fix:** persist each on change via the existing `_remember_*` pattern (a settings round-trip test per mounted key would pin it).

**P1-7 · Settings persistence is an unlocked whole-file read-modify-write — `src/md_llm/core.py:60-75`, `77-114` — core (+ every `_remember_*` caller in controls.py/chat.py)**
Every persist path does `load_settings()` → mutate copy → `save_settings()` which `os.replace`s the entire file. Two concurrent browser sessions interleave and the second save clobbers the first's registry entries/model history; a single chat send performs 2-3 sequential whole-file rewrites, widening the window. Worse, the file is explicitly designed to be shared with the host app (core.py docstring) — md_llm saves erase any host keys written between its load and save. No locking, mtime check, or merge-on-write exists. **Fix:** re-load-and-merge immediately before the atomic replace (merge-on-write), or hold an flock around the RMW.

**P1-8 · A malformed or transiently unreadable settings.json is silently clobbered on next save — `src/md_llm/core.py:74-75` with `103` — core**
`load_settings` catches `ValueError`/`OSError` and returns `{}`; the next `save_settings` then `os.replace`s the corrupt/unreadable file with the near-empty dict. Triggers: a hand-edited file with a trailing comma, a truncated write by a non-atomic third-party tool sharing the file, or a transient permission/NFS hiccup at load time followed by a writable save. No quarantine, no backup, no log — the loss is total and invisible (the write side itself is genuinely atomic and 0600-clamped). **Fix:** when load fails on an existing file, rename it aside (`settings.json.corrupt-<ts>`) before returning `{}`, and log via `console.log_event`/`logging`.

**P1-9 · `launcher.sh` upload purge ignores the dev server — `macos/launcher.sh:174` (purge call) vs `run.sh:60-67` — packaging**
`purge_stale_uploads` (`find ~/.md_llm/uploads -maxdepth 1 -type f -delete`) runs whenever the launcher's own port is unhealthy, but it never probes the dev server's port 8501 — while `run.sh` carefully probes *both* 8599 and 8501 before purging for exactly this reason. Trigger: a dev session (`run.sh`) has browser-uploaded documents open (staged copies are their only copy, per app.py:24-26), and the user then double-clicks any `.md` in Finder; the launcher sees 8599 free, purges, and deletes the dev session's open documents mid-use. The protection is symmetric in one launcher and absent in the other. **Fix:** factor the two-port probe into both launchers (or a shared sourced helper) and refuse to purge while either is healthy.

**P1-10 · Re-staging overwrites staged copies that hold real user edits — `macos/launcher.sh:209-213` (`cp -f`) and both purge sites, vs `src/md_llm/reader.py:496` — packaging/reader seam**
The Reader's editor saves in-app edits *into the staged copy* under `~/.md_llm/uploads` (the README discloses this), but both launchers treat staged copies as disposable re-derivations of the original: `cp -f "$doc" "$UPLOADS_DIR/$(basename "$doc")"` ("the overwrite is the point") and the purges delete them wholesale. Trigger: user edits a doc in the app (Save persists to the staged copy), then re-opens the original from Finder — the in-app edits are silently destroyed with no backup or confirmation. Related: the `cp -f ... || true` at the same line swallows staging failure while `DOCS+=(...)` already recorded the file, so the opened URL can serve stale/absent content as the dropped document. **Fix:** before overwrite/purge, detect edited staged copies (staged mtime newer than source, or an app-written dirty marker) and skip the copy/purge for those, or have app saves write back to the original file so the staged copy really is disposable.

## Architecture assessment

**Structure.** The layering is clean and stable: leaf modules (`state`, `sandbox`, `llm`, `console`) import no Streamlit; panels resolve host facts exclusively through `get_core()`; the provider layer is stdlib-only; `Core`/`init()` remains an excellent host seam. The app/packaging glue is careful (guarded purge in run.sh, correct AppleScript quoting, ad-hoc re-sign).

**Recurring structural weaknesses** (each produced multiple findings above):

1. **Lifetime management at module seams.** Three teardown paths carefully stop streams (session close, clear, resend) but the fourth — document close in `docs.py` — doesn't (P1-2); sandbox GC uses directory mtime as a liveness proxy and reaps live sessions (P1-3); the launchers treat staged uploads as a cache while the editor treats them as storage (P1-10). The pattern: each module's invariant holds inside the module and breaks where ownership crosses to another.
2. **Hand-rolled session-state key lifecycle.** Suffix-based key sweeps (`__doc__<rel>`, `__chat__<n>`) with no escaping keep producing collisions and over-sweeps (P2-36, P2-37) — the same root cause the prior audit flagged. Escaped key components + one centralized sweep entry point would eliminate the family.
3. **Settings persistence has no owner.** Unlocked whole-file RMW shared with hosts (P1-7), silent clobber of malformed files (P1-8), silent save failures (P2-35), and a schema that half the UI reads but nothing writes (P1-6). The layer needs one merge-on-write implementation and an explicit list of persisted keys with a round-trip test.
4. **Duplication with demonstrated drift.** The six provider clients repeat near-identical HTTP and agent-subprocess code; the zcode-only profile-cleanup and cline-only text-drop show the copies have already diverged (P2-7, P2-9, P2-16).

**Trust boundaries are inconsistent.** The Reader enforces `markdown_dirs` containment and realpath checks; the chat context path doesn't (P2-2); and the render path passes raw HTML through (P1-1). One shared "open this path for read/send" choke point plus a sanitization decision would make the story coherent.

**Dependencies & supply chain.** Minimal risk: one runtime dependency (streamlit), stdlib HTTP, no SDKs. The declared floor (`streamlit>=1.44`, pyproject.toml:12) still sits below the behavior the code assumes and documents against 1.58 (app.py:558, chat.py:890/1061) — reconcile the floor.

**Main risks.** (1) Silent data loss: live-sandbox GC, doc-close reply loss, staged-copy edit destruction — all realistic daily-driver flows. (2) The Hardened-sandbox brand promises more than the enforcement delivers in three specifics (P1-4, P1-5, P2-41). (3) XSS the moment a host renders untrusted documents (P1-1).

**Test coverage (cross-cutting).** 482 tests, genuinely strong on plumbing: subprocess argv/parsing, sandbox-profile injection, key lifecycle, staging state machine, atomic-write contracts. Blind spots that mapped directly to this audit's findings: no render-level (AppTest) flows for chat clear/staged-prompt/endpoint switching or `_finalize_all_done_tasks`; the six HTTP wire clients essentially untested except `openai_generate`; no settings round-trip test (would have caught P1-6); close-during-in-flight-stream; the shell scripts are entirely untested.

## Top recommendations

1. **Close the lifetime seams (P1-2, P1-3).** Stop background streams on document close and exclude live sandboxes from GC via an explicit liveness registry (or heartbeat sentinels). These are the most likely ways a daily user loses work today.
2. **Fix the staged-copies data-loss family (P1-9, P1-10).** Give both launchers the same two-port purge probe, and never overwrite/purge a staged copy that holds newer edits than its source — or make app saves write back to the original file.
3. **Make the Hardened sandbox honest (P1-4, P1-5, P2-41).** Prefix-deny the settings staging temps, fail closed (or warn loudly) when sandbox-exec is unavailable, and align the docstring with the actual deny list.
4. **Sanitize Reader HTML (P1-1).** Drop `unsafe_allow_html` or whitelist-sanitize document content before `st.markdown` — the one finding that becomes critical in any multi-user host.
5. **Repair settings persistence (P1-6, P1-7, P1-8, P2-35).** Persist the fourteen orphaned mount keys, switch to merge-on-write (or lock) for the shared file, quarantine malformed files instead of clobbering, and log save failures. Add one round-trip test per mounted key.
6. **Enforce one path guard everywhere (P2-2, P2-21, P2-24).** Route chat context resolution through the Reader's containment check and resolve symlinks for writes.
7. **Consolidate the llm.py provider copies and normalize the error contract (P2-7, P2-10, P2-16).** One agent-subprocess driver and one HTTP client shared by all providers eliminates the drift class; wrap transport errors in the documented `RuntimeError`.
8. **Test the seams (P1-2, P1-6, P2-1 class).** AppTest-level flows for chat clear/close/staged prompts and endpoint switching, wire-contract tests for the streaming HTTP parsers, and a purge-guard test for both launchers.
